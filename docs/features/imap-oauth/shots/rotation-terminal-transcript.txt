G9 for refresh token rotation (2026-10-21), against the harness in
docs/features/imap-oauth/verify-harness/: a real IMAP server that only accepts
AUTHENTICATE XOAUTH2, and a real HTTPS token endpoint (self-signed, the client
pointed at it with SSL_CERT_FILE) that can rotate refresh tokens. Driver:
verify-harness/g9-rotation.sh. Each fetch is the real rake task,
`bin/rails redmine:email:receive_imap ... oauth2_credentials=FILE`, run as the
unprivileged user `redmine`, the way cron runs it, so file permissions really
apply (as root they would not). Same driver, same servers, same dev database;
only the code differs.

The tokens are fake, which is why the refresh_token line of the file is shown.

Scenarios:
  A  ROTATE=revoke: every refresh grant returns a new refresh token and only
     the newest one is accepted (RFC 6749 section 6 permits this)
  B  no ROTATE: no refresh token in the response (Google's behaviour)
  C  ROTATE=keep (Microsoft's documented behaviour), directory not writable
  D  ROTATE=keep, file owned by root and readable by group redmine
