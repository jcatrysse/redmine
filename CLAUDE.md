# CLAUDE.md — GEOxyz Redmine upstream framework

You turn GEOxyz Redmine customisations into patches the Redmine core team
would accept, and keep the GEOxyz branch running the same code so there is
nothing left to maintain privately.

**This branch (`geoxyz/framework`) contains no Redmine code.** It is an orphan
branch holding the rules, the per-feature dossiers, the submitted patches and
the review findings. Nothing here may ever appear in a patch.

## Branch discipline — read this first, every session

| Branch | What it is | Who writes it |
|---|---|---|
| `geoxyz/framework` | this framework — orphan, no Redmine code | you |
| `7.0-stable-GEOxyz` | what GEOxyz actually runs | you, via a worktree |
| `patch/<slug>` | one upstream patch, branched from `origin/master` | you, via a worktree |
| `origin/master` | Redmine trunk mirror — the target for every patch | nobody |
| `origin/7.0-stable` | upstream 7.0 — the base of the GEOxyz branch | nobody |

**The branch name above is pinned.** Jan authorised pushing to
`geoxyz/framework` on 2026-09-01, and that authorisation overrides whatever
branch the execution environment prescribes for the session. The environment
mints a fresh branch name per session; if a session starts somewhere else, do
not commit there — check out `geoxyz/framework` (creating it from the remote if
needed) and say so in the report.

Home base is this branch. All real work happens in worktrees beside it:

    /home/user/redmine          this branch — the rules live here
    /home/user/wt/geoxyz        7.0-stable-GEOxyz
    /home/user/wt/patch-<slug>  patch/<slug>, branched from origin/master

A patch branch is **always** created from a fresh `origin/master`, never from
`7.0-stable-GEOxyz` and never from this branch. That is what makes it
structurally impossible for a framework file to reach a patch.

    git fetch origin master
    git worktree add -b patch/<slug> /home/user/wt/patch-<slug> origin/master

## What Jan tells you, and what you do when he doesn't

Two axes: **what** (which feature) and **where** (GEOxyz, upstream, or both).

**Both, upstream-shaped, is the normal case — not an option to offer.** The
whole point is that GEOxyz runs the code that upstream accepts, so the eventual
merge is a no-op. Build the upstream design first, then apply that same design
to the GEOxyz branch.

Ask about *where* only when it is genuinely ambiguous:

- a local-only item (host allowlist, `.gitignore`, an ops rake task with a
  hardcoded group name) → GEOxyz only, no patch, no dossier beyond one line
- a feature where upstream will plausibly accept less than GEOxyz needs → a
  real choice, and it belongs to Jan (see Class B)

If he does not say *what*, take the next row from the register in
`docs/STATE.md`.

## Invariants — refusal conditions

Refuse to write, and flag, any change that violates one of these, even if a
task description seems to ask for it.

- **INV-1 Minimal diff.** Only what the feature needs. No reformatting, no
  tidying, no improving adjacent code, no renaming. If you notice something
  wrong nearby, report it — do not fix it in the patch.
- **INV-2 Every patch applies standalone** to a fresh `origin/master`. Patches
  never stack on each other.
- **INV-3 No explanatory comments.** Redmine's codebase is almost
  comment-free. A comment is allowed only for a non-obvious *why*, never for
  what the code does.
- **INV-4 No AI traces** anywhere that reaches the repo or a patch: no
  `Co-authored-by` to a tool, no "generated by", no model names, no TODOs of
  your own making.
- **INV-5 Locales: `en`, `nl`, `fr`, `de`, `es` — nothing else, and every
  translation is derived, never invented.** Jan's decision (2026-09-01): these
  four languages ship with the work. The rule that makes that safe: for each
  new key, find the closest existing key in that same locale file and match its
  terminology, register and capitalisation — then name that key in the dossier
  so anyone can check it in seconds. Redmine's own files disagree on basic
  vocabulary (`issues` is *issues* in Dutch, *demandes* in French, *Tickets* in
  German, *peticiones* in Spanish), so a translation written from scratch is
  plausible and wrong. See `docs/redmine-requirements.md`.
- **INV-6 No new gem, migration, setting, route or permission** without an
  explicit justification in the dossier. The null hypothesis is that it is not
  needed.
- **INV-7 Never disable, skip, weaken or delete a test** to get green. A test
  whose assertion is genuinely wrong is a finding to state plainly, not an
  obstacle to route around.
- **INV-8 Green means proven green.** You ran the suite and RuboCop, you saw
  the output, and the counts are written in the dossier. "Should work",
  "tests added" and "verified locally" without numbers are not green. This is
  the invariant the previous attempt at this work broke; treat it as the
  important one.
- **INV-9 No framework file in a patch.** `tools/check-patch-clean.sh` must
  pass before any export.
- **INV-10 GEOxyz and upstream behave identically** unless the dossier records
  the divergence, its reason, and that it is a permanent private patch.

## Forbidden constructs

Every row below is a real defect found in the existing GEOxyz code or its
2026 port. They are grep-able on purpose.

| Forbidden | Why | Instead |
|---|---|---|
| `Co-authored-by:` to a tool, `Generated by`, a model name | INV-4 | nothing |
| a comment restating what the line does | INV-3 | delete it |
| `.html_safe` on text from user, SCM or mail input | injection surface | `safe_join`, or leave the escaping alone |
| top-level `def` in a `.rake` file | defines private methods on `Object` for the whole app | a module or class under `lib/redmine/` |
| a top-level constant in a `.rake` file | same, on `Object` | namespace it |
| `require_relative` to a file under an autoload path | breaks Zeitwerk for the rest of the namespace | just name the constant |
| assigning an instance variable inside a view or partial | Rails antipattern, leaks across loop iterations | pass it as a helper argument |
| an SCM call per row inside a view loop | N subprocesses per page view | one call, or cache it |
| a locale file outside en/nl/fr/de/es | INV-5 | leave it to Redmine's translators |
| a translation written from scratch instead of patterned on an existing key in the same file | reads plausible, uses the wrong Redmine term | find the nearest existing key, match it, cite it in the dossier |
| `sub(...)` where every occurrence must go | silently sanitises only the first | `gsub` |
| a safe-navigation chain (`a&.b.c`) | works by accident on `nil` | guard properly |
| a test method that reimplements the code it tests | passes even when both are wrong | call the production code, assert literal values |
| `git format-patch` from a branch not descended from `origin/master` | INV-2, INV-9 | recreate the branch from trunk |
| trailing whitespace, missing final newline | half of the port's 73 lint offences | `rubocop -a` before committing |

## Quality gates — all must pass with evidence

| Gate | Check |
|---|---|
| **G1 Trunk check** | does current trunk already solve this? Done **first**, recorded in the dossier. One GEOxyz feature already landed upstream on its own; do not rebuild what exists. |
| **G2 Correctness** | behaviour demonstrated, edge cases named, failure modes safe |
| **G3 Tests** | relevant suites green, output seen, counts in the dossier; each new test red on the old code, and you say how you know |
| **G4 Lint** | `rubocop` clean on the changed files, and the baseline for those files was clean too |
| **G5 Minimality** | you re-read the diff adversarially and every line is defensible; no scope creep |
| **G6 Patch hygiene** | applies to a pristine trunk checkout; `tools/check-patch-clean.sh` passes |
| **G7 Dossier** | complete, including anticipated objections with answers |

A red suite, a lint offence or an invariant hit is a blocker: fix it and re-run
the gates on the delta.

## Cadence — stop and show, per feature

**This is deliberately the opposite of the `redmine_ai_triage` framework's
"keep going" rule.** There, autonomy is the point because Jan is not watching.
Here, every feature is a judgement about what upstream will accept, and Jan
files the issues himself. So: finish one feature completely — dossier, patch,
GEOxyz commit, gates green — then stop and report. Do not start the next
feature.

Within a feature, do not stop: make Class A decisions, log Class B ones, keep
building.

## Decisions

- **Class A — obvious.** Best practice, an established Redmine convention, or
  the framework already decides it. Decide yourself, one line in
  `docs/DECISIONS.md`.
- **Class B — Jan's, but deferrable.** Taste, user-visible naming, thresholds,
  and above all *how much scope to give up to get a patch accepted*. Do not
  stop mid-feature. Pick the option most likely to be accepted upstream,
  implement it, and log it under "Open — keuze voor Jan" with the options, a
  plain-language explanation of each, and your recommendation.
- **Class C — blocking.** Stop cleanly: leave the worktrees green, update
  `docs/STATE.md`, report.

## Stop and ask Jan when

- Upstream will plausibly accept materially less than GEOxyz needs, so the
  choice is "live with less" versus "keep a permanent private patch".
- A feature needs a schema change that does not belong in a first patch.
- Anything would send real data to an external service (the OAuth
  authorisation flow needs a human and real credentials — it can never be a
  test).
- A review finding would require relaxing one of INV-1..10. That is a
  conversation, not a code decision.

## Continuity — the branch is the memory

- **`docs/redmine-requirements.md`** — what Redmine actually requires, with the
  source for each claim. Read it before assuming a convention; do not re-derive
  it every session.
- **`docs/STATE.md`** — overwritten every session. Where we are, the feature
  register (status per feature, patch branch, issue number, submission state),
  what landed last, the exact next step, known traps. Write it as if the next
  session knows nothing.
- **`docs/DECISIONS.md`** — append-only. "Beslist (autonoom)" one-liners, and
  "Open — keuze voor Jan" with options, explanation and a recommendation.
- **`docs/features/<slug>.md`** — the submission dossier, from
  `docs/features/TEMPLATE.md`. The sections that become the redmine.org issue
  are written in **English**, ready to paste; the "Voor Jan" block at the top
  is Dutch.
- **`patches/<slug>/<date>-r<rev>.patch`** — exactly what was attached to the
  issue, committed so it can be diffed against later feedback.
- **`docs/review/findings/<date>-<reviewer>.md`** — one file per review run,
  from the template. A reviewer never changes code; a fixer never weakens a
  test; every open finding gets a `Resolution:` line, and "ran out of time" is
  an acceptable reason while silence is not.

## Commits on this branch

Atomic, message = what changed and why in one line. Push after every commit.
No PRs — this branch is Jan's working memory, not a proposal.

Commits on `7.0-stable-GEOxyz` and `patch/<slug>` follow Redmine's own
conventions instead: a descriptive subject with the redmine.org issue number
once one exists, no prefix scheme of our own, and nothing from INV-4.
